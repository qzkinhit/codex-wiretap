# Security and local data

Pool Router binds only to a loopback address. Management endpoints and the pool-backed model path require the generated local token. Host and Origin checks reject cross-site access.

When legacy monitoring is enabled, the two Responses POST endpoints may accept a caller-provided `sk-` credential. This path forwards only that credential to the original provider address stored in the private recovery backup created before integration. Forwarding is rejected if compatibility integration is incomplete or the backup is invalid; the application does not guess the destination for the caller’s key. It cannot select stored pool credentials or access management endpoints and the model list.

Legacy monitoring forwards the original request body once, without pool retries, account substitution, model overrides, session recovery, compaction repair, or image compression. Its upstream traffic is outside the pool scheduler's concurrency counters.

Automatic pool source selection uses an explicit `upstream_base_url` or the unique HTTPS Responses upstream discovered in BiWrite. Switching from automatic to manual mode saves the most recently resolved upstream when no explicit address is supplied. Manual mode requires a stored address and rejects forwarding when it is absent; it does not follow subsequent changes in BiWrite. Ambiguous discovery requires an explicit selection. Accepted addresses use a public domain name, HTTPS on the default port, and a root or `/v1` path. User information, query parameters, fragments, and other paths are rejected. Manual credentials are sent to the selected pool upstream.

BiWrite credentials are read into memory. Optional `biwrite_import_all` continuously includes all configured keys at the selected upstream, including ignored, stopped, and non-keep-alive keys; it defaults to false and does not imply verified health. `sync_paused` pauses scheduled source reads, retaining the current pool. Startup always reads the current source once to initialize the pool, even with a saved pause; subsequent periodic reads respect `sync_paused`. A manual single sync does not clear that pause. Sanitized labels from `keyNames` may be shown in the dashboard; labels should not contain sensitive information. Manually added credentials are stored in `manual-keys.json` in the private application data directory. Configuration and recovery backups can contain credentials. These files are private local state and must not be included in bug reports or commits. The application uses owner-only file permissions on Unix systems.

Ordinary gateway monitoring stores allowlisted metadata and bounded, redacted error messages in `AttemptRecord.error_message`. Each request retains at most 100 attempt records; error messages are limited to 2 KiB each and 16 KiB in total per request. It does not retain complete request bodies, successful response bodies, authorization headers, or complete upstream error responses. Error summaries are diagnostic text supplied by an upstream; redaction does not make every possible message safe to publish. Review summaries and account labels before sharing local logs or screenshots. Gateway action records describe retries, session resets, compaction repairs, and image size changes without storing the affected content.

Fixed account probes send only the application-defined short prompt and may return limited visible response text, including successful output, safe error classifications, usage, and event details. This is separate from ordinary gateway logging. The dashboard allowlists, redacts, and renders probe details as text, retaining only the latest result per account in page memory, never in persistent browser storage. It does not display authorization headers, credentials, encrypted reasoning, or user conversation bodies. Model, reasoning and service-tier values are upstream declarations, not independent verification of execution or billing. Published screenshots use synthetic data.

A pool attempt with no response headers after `hedge_after_ms` (default 20000, 0 disables) is raced against one other candidate account. The same request body is sent to the same upstream under that second account's credential, so both accounts may be billed for it and both may execute it; the loser is dropped, which cancels its connection but does not prove the upstream stopped work. The race starts only while no response headers exist, so the client can never receive content from both. The winner's account is the one recorded and charged in the local ledger. Hedging is skipped when no candidate is free, when the request is bound through `previous_response_id`, or when too little header wait remains in the attempt.

Pool requests default to 15 retries, or 16 attempts including the first request (`max_attempts = 16`); the dashboard edits the retry count. The default first meaningful output deadline is 120 seconds per attempt. A request without `previous_response_id` can be retried after that deadline while no meaningful output has appeared, but timeout does not prove that the upstream did not execute it. Once meaningful text, reasoning, or tool output appears, the proxy does not automatically replay the request. A request bound through `previous_response_id` cannot be rebuilt on another account; unknown or unavailable bindings fail explicitly. The response ID also pins its actual upstream session mapping or original unmodified state, so a later scope-level session reset cannot redirect an existing continuation to a newer mapping.

Session recovery and compaction repair are enabled by default and remain subject to the request's overall attempt and time limits. Session identifier recovery is limited to once per request, before meaningful output, after persistent 429 responses or an explicit bound-resource 502, and cannot reset a request containing `previous_response_id`. Existing recovery mappings are scoped to the conversation, account, model, and upstream. Compaction repair removes affected opaque encrypted reasoning or compaction items only after an explicit incompatible-encrypted-content HTTP 400 from `/v1/responses/compact`, with at most one repair retry. Available plaintext and tool relationships are retained, but context present only in removed items can be lost. Generic 400 errors and successful responses do not trigger this repair. Neither feature reconstructs omitted conversation history or guarantees compatibility with a particular upstream.

Optional image compression defaults to off. It processes only inline PNG/JPEG data in request messages, never fetches remote image URLs, and applies bounded input and decoding budgets. Eligible images may lose resolution and are encoded as lossy JPEG; transparent areas are composited onto white. Unsupported, malformed, animated, or over-budget images remain unchanged. Only size and count summaries are recorded.

Do not put credentials in public GitHub issues. Use GitHub private vulnerability reporting if it is enabled for this repository; otherwise contact the repository owner without including a working credential or private conversation.
